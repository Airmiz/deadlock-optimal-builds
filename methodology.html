1. Overview

This project derives optimal item builds and ability orders for every playable Deadlock hero from public match data. Nothing is hand-curated — every recommendation is a function of the public API plus the algorithms below. If you can read the API and reproduce the algorithms, you get the same builds.

The page is patch-aware: each patch's data lives under its own namespace so multiple patches can be browsed side-by-side. When Valve ships a balance patch, the pipeline re-runs against the new patch's match data and the recommendations update — usually within hours of release once enough matches accumulate.

Design principle. Every number on the page is a function of an API response and a documented formula. If you click an item, you should be able to trace the score back to wins, losses, and matches at the API level.

4. Wilson lower bound

For every item, the API gives wins and matches. The naive win rate $\hat{p} = \text{wins}/\text{matches}$ is unreliable on small samples — a 60% win rate over 5 matches tells you almost nothing about the true win rate.

Wilson's score interval at 95% confidence gives a defensible lower bound on the true win rate that automatically penalizes small samples:

$$ W_{\mathrm{LB}}(\text{wins}, n) = \frac{\hat{p} + \frac{z^2}{2n} - z\sqrt{\frac{\hat{p}(1-\hat{p})}{n} + \frac{z^2}{4n^2}}}{1 + \frac{z^2}{n}} $$

where $\hat{p} = \text{wins}/n$, $n = \text{matches}$, and $z = 1.96$ for a 95% confidence level.

The optimizer's score for an item is then:

$$ \text{score} = W_{\mathrm{LB}}(\text{wins}, n) - \text{baseline\_WR} $$

so positive scores mean "this item makes the hero better than that hero's average".

Worked example: Boundless Spirit on Shiv (high MMR)

From cache/patch_125825/hero_data/itemstats_hmmr_19.json, the entry for Boundless Spirit (id=1835738020): 

wins   = 10,389
losses =  8,765
matches = 19,154

So $\hat{p} = 10389/19154 = 0.5424$ — a raw 54.24% win rate. Plugging into the Wilson formula:

$$ W_{\mathrm{LB}} = \frac{0.5424 + \frac{3.84}{38308} - 1.96\sqrt{\frac{0.5424 \cdot 0.4576}{19154} + \frac{3.84}{1.46\!\times\!10^9}}}{1 + \frac{3.84}{19154}} \approx 0.5353 $$

So Wilson LB ≈ 53.53%, almost identical to the raw WR because the sample is large. With Shiv's high-MMR baseline of 47.35%, the score is:

$$ \text{score} = 0.5353 - 0.4735 = 0.0618 $$

i.e. Boundless Spirit on Shiv beats the baseline by +6.18 percentage points. The optimizer ranks items by this score.

Why Wilson and not raw WR? Because the cost of being wrong matters. An item with 50 matches and 60% WR gets a Wilson LB closer to 47% — the optimizer correctly de-prioritizes it relative to a 5,000-match item at 53% (which keeps its 53%). At 50,000 matches the methods agree to four decimal places. Wilson smoothly trades raw signal for sample-size confidence.

6. Three build methods

The page surfaces the synergy-aware ILP as the default Recommended build. The full per-hero JSON in heroes/<patch_id>/ carries all three for inspection.

Method 1: Wilson Greedy

Rank items by score, take top 4 per category + 4 flex. Simple and defensible.

for cat in (weapon, vitality, spirit):
    pick top 4 candidates by score in this category
flex = top 4 from remaining pool by score

Bias: prefers high-WR late-game items because they have tighter confidence intervals.

Method 2: Synergy-aware ILP (default)

Linear program that maximizes individual scores PLUS pairwise synergy bonuses, subject to slot constraints:

$$ \max \sum_{i \in I} \text{score}_i \cdot x_i \;+\; \sum_{(i,j) \in P} \text{synergy}_{ij} \cdot y_{ij} $$

subject to:

  • $x_i \in \{0,1\}$ — pick decision per item
  • $y_{ij} \in \{0,1\}$ — pair-active when both picked: $y_{ij} \le x_i$, $y_{ij} \le x_j$, $y_{ij} \ge x_i + x_j - 1$
  • $\sum_{i \in C_k} x_i \ge 4$ for each category $C_k$ (weapon / vitality / spirit)
  • $\sum_{i} x_i = 16$ (16-slot inventory)
  • at most one $x_i$ per upgrade-chain lineage (lineage dedup, see §10)

The pairwise synergy bonus comes from /v1/analytics/item-permutation-stats with comb_size=2:

$$ \text{synergy}_{ij} = (\text{WR}_{ij} - \overline{\text{WR}}_{i,j}) \cdot w_{ij} $$

where $\overline{\text{WR}}_{i,j}$ is the average of items $i$ and $j$'s individual WRs, and $w_{ij} = \min(1, n_{ij}/k)$ is a sample-size weight ($k$ defaults to $4 \times \text{pair\_floor}$). The top-400 strongest synergies feed the LP to keep it tractable.

Solved with CBC via PuLP, time-limited to 4 seconds per hero — finds a feasible solution almost instantly; the time limit is for proving optimality.

Method 3: Build Replication

Aggregate items across the highest-WR community builds, weighted by:

$$ w_{\text{build}} = \text{matches} \cdot \max\!\left(0,\; \text{WR}_{\text{build}} - \text{baseline\_WR} + 0.02\right) $$

Then pick top 4 per category by build-frequency-weight + 4 flex from remaining.

What this captures that Wilson and ILP miss: situational utility items (Counter Spell, Dispel Magic, Metal Skin, Healbane) that don't have impressive standalone win rates but appear in every winning build because they're how high-MMR players survive long enough to use the rest of their kit.

Why three? Each captures a different signal. Wilson tells you "what wins given enough data". ILP tells you "what wins together". Replication tells you "what real winning humans buy". Disagreements between them are diagnostic — they're how you spot selection bias and missing utility items.

7. Item tags

Every pick on the page wears one of four tag colors based on how often it appears across the community's top builds for this hero:

SIT.≤ 30%counter / utility role; appears in some builds
STATn/apurely stat-derived: optimizer found this WR, no community build uses it
About STAT picks. The optimizer found a winning item that the community hasn't validated. It could be a hidden gem, or it could be sample noise the community has correctly identified as a trap. Treat with appropriate skepticism — these are bets, not consensus. Patches with thin data (e.g. brand-new patches) tend to have lots of STAT picks.

8. Signature items (hero affinity)

The gold ⭐ on certain item rows marks a hero affinity score above a threshold. Affinity is a hero's pick rate for an item, normalized by the average across all heroes:

$$ \text{affinity}_{h,i} = \frac{P(i \mid \text{hero}=h)}{\bar{P}(i)} \quad\text{where}\quad \bar{P}(i) = \tfrac{1}{38} \sum_{h'} P(i \mid \text{hero}=h') $$

An item is tagged signature if it satisfies both:

  • $\text{affinity}_{h,i} \ge 2.0$ — this hero picks it ≥2× the average hero
  • $P(i \mid \text{hero}=h) \ge 0.30$ — the hero picks it in ≥30% of top builds
Worked example. Infuser (T4 vitality, $6,400) appears in 50% of Shiv's top high-MMR builds, but only 9% of the average hero's. So affinity = 0.50 / 0.09 ≈ 5.6×. Both conditions clear, and Infuser earns a ⭐ on Shiv's recommended build. On Lash, Infuser's pick rate is comparable to the average hero's — no star, even though both heroes deal spirit damage.

9. Investment-spike progression

Deadlock has cumulative gold-spent thresholds per category. At each threshold, your damage / health / spirit-power gets a percentage bonus. Bonuses are mostly small until 4,800 souls — there the bonus more than doubles. The page calls this the major spike.

The thresholds are universal across heroes: 800, 1,600, 2,400, 3,200, 4,800, 7,200, 9,600, 16,000.

10. Lineage chains

Some Deadlock items have an upgrade-component relationship — buying the higher tier consumes the lower-tier component. They share an inventory slot:

Extra Spirit (T1, $800)
  ↓ upgrades to
Improved Spirit (T2, $1,600)
  ↓ upgrades to
Boundless Spirit (T4, $6,400)

The optimizer applies lineage dedup: within an upgrade family, only one slot. This used to be a real problem — earlier builds showed both Extra Spirit and Boundless Spirit in two separate slots, double-counting cost and slot economy.

Lineages are computed by union-find on the directed component-edge graph extracted from the asset metadata's component_items field. Items in the same union are forbidden from co-occurring in a build.

Audit before/after the fix. Before lineage dedup, 35 of 38 heroes had at least one chain conflict in their recommended build (78 conflict pairs total). After dedup, every recommended build holds 16 distinct lineages.

The page surfaces the chain visually: each lower-tier ancestor renders as its own stage row in the phase column matching its actual buy time, with a "↑ upgrades into X in late game" footer. So you see when to buy Extra Spirit (~10 min) AND when it becomes Boundless Spirit (~30 min) — same slot, different items in time.

11. Sell events

The API returns an avg_sell_time_s for every item. Real Deadlock builds are buy timelines, not snapshots — early/mid items get sold to free slots for late-game purchases.

The page surfaces a ↓ Sell event in the destination phase column when all of the following hold:

  • $\text{sell\_min} - \text{buy\_min} \ge 6$ minutes (real strategic sell, not match-end noise)
  • item was bought in early or mid phase (T4 picks aren't sold)
  • $\text{sell\_min} \lt 38$ (otherwise it's just match-end)

Refund estimate is ~50% of cost — the Deadlock convention. Sell rows have a red dashed border to distinguish them from buy rows.

Shiv example. Restorative Shot (T1 weapon, $800) is bought at minute 1.8 and sold at minute 24.4 — held 22.6 minutes. Hits all three filters → renders a sell event in the late phase column. Witchmail (T4 vitality, $6,400) is bought at minute 31.8 and "sold" at minute 32.1 — that's match-end noise, filtered out.

13. Archetype clustering

For each hero, the cached community top builds are clustered by Jaccard distance on item sets:

$$ d_J(A, B) = 1 - \frac{|A \cap B|}{|A \cup B|} $$

where $A$ and $B$ are the item-id sets of two builds. Average-linkage agglomerative clustering merges the closest pairs until we hit a target $k$ ($k \in \{1,2,3\}$ depending on build count).

Per-cluster optimization (the synergy_ilp build_method)

Each meaningful cluster (≥2 builds) gets its own stat-optimized build. The synergy ILP is re-run with the candidate pool restricted to items appearing in ≥30% of the cluster's builds (relaxes to 15% if no feasible 16-slot build exists otherwise).

Result: each archetype produces a build that's both stat-optimized AND archetype-coherent, instead of the popularity-aggregate fallback.

Seven on patch_125825. Two clusters cleanly separate:
  • Suppressor build (75% of top builds, 56.34% avg WR) — gun-pressure: Mercurial Magnum, Crippling Headshot, Spiritual Overflow
  • Mystic Reverb build (17%, 56.19% avg WR) — anti-gun spirit: Bullet Resist Shredder, Counterspell, Mystic Reverb, Inhibitor
Both run through the synergy ILP scoped to their cluster's vocabulary and produce different, internally coherent builds.

14. Counter-pick panel

For every (hero, enemy_hero) pair, we pull /v1/analytics/item-stats?hero_id=X&enemy_hero_ids=Y and compute, per item, the win-rate delta against the no-enemy-filter baseline:

$$ \Delta_{i, h, e} = \mathrm{WR}(i \mid \text{hero}=h, \text{enemy}=e) - \mathrm{WR}(i \mid \text{hero}=h) $$

Positive delta = item works better than usual when enemy $e$ is on the field.

Aggregating across selected enemies

When the user selects multiple enemies $\{e_1, e_2, \ldots, e_k\}$ in the panel, the page sums per-item deltas:

$$ \text{matchup\_score}_{i, h, S} = \sum_{e \in S} \Delta_{i, h, e} $$

Top items by positive matchup_score are the buy recommendations; bottom items are the avoid recommendations.

Filters (so the signal isn't noise)

  • $n_{\text{vs}} \ge 100$ matches in the matchup-specific slice
  • $n_{\text{baseline}} \ge 200$
  • $|\Delta| \ge 0.4\text{pp}$
  • Top 12 stored per pair, ranked by $|\Delta|$

15. Per-patch item overrides

The asset CDN at assets.deadlock-api.com can lag a Deadlock patch by hours-to-days. When a patch ships, items like Shadow Weave can show their pre-patch tier/cost/cooldown values in our cache.

ITEM_OVERRIDES_BY_PATCH in scripts/build_page_data.py is a small per-patch dict that hand-codes corrections from the patch notes. Applied at compact-hero time so each patch shows its own correct values.

Shadow Weave timeline. Patch 04-30-2026 moved Shadow Weave from T4 to T3, dropped its cost from $6,400 to $3,200, and lengthened its cooldown from 32s to 45s. The asset CDN didn't update for several hours after release, so the page would have shown the old values on the new patch. The override entry corrects this until the CDN catches up: 
"patch_129989": {
    1798666702: {"tier": 3, "cost": 3200, "cooldown_s": 45},  # Shadow Weave
    ...
}

Once the asset CDN refreshes, the override entries should be deleted and the cache refetched — at that point the items.json will carry the correct values natively.

16. Ability priority

Per hero, /v1/analytics/ability-order-stats returns ordered sequences of ability point spends with wins, losses, matches, plus aggregate stats. From these we compute three signals:

Winner-weighted AP investment

For each ability, the average AP spent on it weighted by wins only, alongside the population-average:

$$ \overline{\text{AP}}^{\text{winners}}_a = \frac{\sum_o W_o \cdot \mathrm{count}(a, o)}{\sum_o W_o} \,,\qquad \overline{\text{AP}}^{\text{pop}}_a = \frac{\sum_o N_o \cdot \mathrm{count}(a, o)}{\sum_o N_o} $$

where the sum is over ability orders $o$ in the data, $W_o$ is wins on that order, $N_o$ is matches, and $\mathrm{count}(a, o)$ is the number of times ability $a$ appears in $o$.

The winner premium $\overline{\text{AP}}^{\text{winners}}_a - \overline{\text{AP}}^{\text{pop}}_a$ is the cleanest "what should I do differently" signal in the dataset — a positive premium means winners invest in this ability more than the average player.

The ordered first-4-points pattern with highest WR over enough sample (≥400 all-MMR / ≥200 high-MMR).

Best full sequence

17. Pipeline reproducibility

Every script is patch-aware via the PATCH_ID env var, idempotent (skips already-cached files), and self-contained.

PATCH_ID=patch_129989 python3 scripts/batch_fetch.py        # ~1 min for fresh fetch
PATCH_ID=patch_129989 python3 scripts/batch_fetch_builds.py # community build details
PATCH_ID=patch_125825 python3 scripts/batch_fetch_counters.py # matchup data
PATCH_ID=patch_129989 python3 scripts/run_all_heroes.py     # generate per-hero JSONs
python3 scripts/build_page_data.py                           # multi-patch payload
python3 scripts/download_images.py                           # localize image refs
python3 scripts/build_page.py                                # assemble HTML

The pipeline auto-runs every 3 hours via GitHub Actions (.github/workflows/refresh.yml) and deploys to GitHub Pages. Each run takes ~2-3 minutes warm-cache (the cache directory is persisted across runs via actions/cache@v4).

18. What this project doesn't do

Honest list of methodology gaps:

  • Live MMR-stratification within High MMR. Phantom-1 vs Eternus-6 isn't broken out; would help but the sample sizes get tiny.
  • Hierarchical pooling for low-pick heroes. Vyper / Sinclair-class heroes have sparse per-hero data; pooling across heroes via a multi-level model would help.
  • Provably-optimal CBC convergence. The 4-second timeout sometimes leaves provably-optimal slack, but the difference is rounding-error per pick.
  • Bayesian shrinkage as an alternative to Wilson. Analyzed in analysis/wilson_vs_bayesian.py — found ~4% pick changes, not worth the new hyperparameter.
  • Real-time match data. Refresh is a 3-hour cadence; faster than that hits the API's 1-hour cache TTL anyway.
  • Causal vs observational. All recommendations are observational. We don't claim "buy this and you'll win"; we show "winners on this hero buy this".
